# CLAUDE.md — NOC Multi-Monitor Display App

This file gives Claude Code the standing context for this project. Read `noc-display-app-spec.md` in full before starting any work — it contains the complete product spec, architecture, and every decision made so far. This file summarizes the parts that most affect how code should be written.

## What this app is
A Windows desktop app for a single NOC/datacenter workstation. It drives 6 monitors connected through a fixed-grid HDMI video-wall splitter (not true independent multi-monitor output), pinning specific dashboards/apps to specific screen regions and keeping them running reliably, unattended, for long stretches.

## The one thing to never forget
**Windows only ever sees ONE virtual display.** The hub physically slices one combined video signal into a grid — it does not give the OS 6 independent monitors. This means:
- Do NOT use `System.Windows.Forms.Screen.AllScreens` or native multi-monitor APIs to detect "monitors" — there's only one, from Windows' point of view.
- The app itself is the compositor: one fullscreen borderless window, subdivided into cells that are rendered/positioned to match the hub's physical cut points exactly.
- Cell pixel boundaries must come from the hub's actual spec (input resolution + grid mode), never estimated or hardcoded from a guess.

## Tech stack
- **C# / .NET** (current LTS)
- **WPF** for the compositor window and editor UI
- **WebView2** for any browser/URL-based dashboard cell (this covers most cells — most dashboards here are web-based)
- **Win32 P/Invoke** (`SetParent`, related window APIs) for reparenting native (non-browser) app windows into a cell. Capture-based rendering (Windows Graphics Capture API) is NOT needed for v1 — all target dashboard apps are standard windowed apps with no hardware-accelerated rendering.

## Key architectural decisions (do not relitigate without checking with the user)
- Cells stay clickable/interactive — this is not a pure read-only display. No "lock" mechanism against accidental clicks.
- Went-dark and frozen-content detection share the same visual indicator (red cell border). The activity log, not the UI, is where the two are distinguished.
- Watchdog relaunch shows a visible "restarting" state on the cell — never a silent relaunch.
- App auto-launches on Windows startup via an auto-login kiosk session — do not build a "wait for manual login" path.
- Switching split presets (e.g. 2x3 → 2x2) preserves bindings for cells that become hidden, so switching back restores them. Do not discard bindings on preset switch.
- Activity log is a plain text/log file on disk — no in-app log viewer needed for v1. Every entry includes timestamp + cell.
- Manual profile switching only for v1 (editor + a dedicated quick-switch hotkey). Do not build scheduled auto-switching yet, but keep the profile-switching code structured so it can be added later without a rewrite.
- Global dim/blank and manual snapshot export are each their own separate dedicated hotkey — do not combine into one modifier+key scheme.
- No idle/burn-in protection — monitors are powered off after hours, so this isn't needed.
- No cross-cell spanning layouts in v1 — cells are fixed rectangles for now.
- No remote management, no multi-workstation sync, no external alerting integrations (Slack/PagerDuty/email), no scripting/plugin engine — these are explicitly out of scope for v1. Do not add them speculatively.

Follow the phase order in the spec's "Procedural Roadmap" and "Timeline" sections: Foundation → Reliability → Content refresh → Polish. ## Native app reparenting: real limitations found on hardware (2026-09-16)
Tested against Windows 11's built-in Notepad, Paint, and File Explorer as stand-ins while gathering the real app list. All three are modern MSIX-packaged/singleton apps, which don't behave like the "standard windowed apps" the architecture assumes:
- **Notepad:** MSIX redirection stub — the launched process never produces a discoverable window and just sits there until our timeout kills it. `NativeAppHost.AttachAsync` correctly times out, retries, and gives up after 5 attempts without leaking processes (fixed two real bugs here: cells that failed on their *first* attempt used to never retry, and overlapping watchdog-triggered retries used to leak an orphaned process per attempt).
- **File Explorer:** now **actually works**, not just fails cleanly. `explorer.exe` hands the request to the already-running shell (which opens a real window on the desktop) and exits immediately, rather than hanging around to time out — so tracking our own launched process was always going to fail. **Fixed 2026-09-17:** `NativeAppHost` special-cases `explorer.exe` — `AttachShellWindowAsync` snapshots existing top-level windows of class `CabinetWClass` (File Explorer's window class, stable since Vista), launches the process, then polls for a *new* one that appears and reparents that directly, regardless of which process created it. Since the window belongs to the persistent shell process (never to be killed or `CloseMainWindow()`'d), `AttachResult.Process` is left null and `CellRuntime.TrackedWindowHandle` tracks it instead — watchdog liveness uses `IsWindowAlive` (not `Process.HasExited`) and cleanup uses `CloseWindow` (`PostMessage(WM_CLOSE)` to that one window, never touching the shell process). Verified live: real Explorer content renders in the cell with a correct green border, exactly one window opens (no more stray-window spam from the old retry-5-times behavior), and closing the window is correctly detected and relaunched by the watchdog.
- Other apps with a similar "hands off and exits" pattern than Explorer's (not yet seen, but plausible) still fall back to the old behavior: `ProcessExitedWithoutWindowException` distinguishes "exited immediately, side effect likely already happened" from "timed out, probably still stuck" — the former gives up after one attempt instead of retrying, since retrying would only repeat an uncontrolled side effect we can't detect and reparent (no known window class to watch for).
- **Paint:** reparents and renders live content correctly in most tests. **One intermittent glitch observed 2026-09-16:** when 2-3 native apps launch concurrently (e.g. two Paint instances + Character Map together), one cell occasionally displays another cell's visual content — confirmed via `GetWindowThreadProcessId` that the window's position and process ownership were both correct, only the rendered pixels were wrong, and a forced `RedrawWindow` didn't fix it. Not reproduced on every run; suspected DirectComposition/rendering-pipeline timing issue specific to modern Fluent-UI (WinUI/Islands-hosted) apps under concurrent-launch stress, not a positioning or ownership bug. Not fixed — would need much deeper investigation into Windows' composition surface handling for reparented Islands-hosted windows.

**Fixed same day:** reparented apps were rendering across the whole display instead of being confined to their cell. Two root causes, both fixed:
1. `SetParent` alone does not turn a window into a real Win32 child — per Microsoft's own docs, it doesn't touch the `WS_CHILD`/`WS_POPUP` style bits. Without explicitly flipping those, the window keeps behaving like an independent top-level window regardless of what `SetParent` reports. Fixed in `NativeAppHost.Reparent`.
2. The compositor process had no explicit DPI-awareness manifest, causing Windows to virtualize the coordinates/sizes passed to `SetWindowPos` for reparented windows (observed as an exact 0.8x = 1/1.25 scale-down, matching this machine's 125% display scaling). Fixed with an explicit `PerMonitorV2` `app.manifest`.

After both fixes, X-position and width land exactly on the cell boundary in every tested preset, confirmed on the physical 6-monitor wall — no more bleeding across monitors.

**Height-clamp red herring, resolved 2026-09-16:** Character Map and Paint initially appeared to consistently clamp their own height to ~82% of whatever was requested (e.g. asked for 1080, settled at 881), and overshooting the request to compensate made no difference. Root cause turned out to be the *dev test setup*, not the app or the reparenting code: the test script always launched the compositor on the primary monitor, then moved it to the hub display with `SetWindowPos` afterward — Paint computed its internal layout against the primary monitor's work area (1536x864) before that move, and never revisited it despite the later reparent. Confirmed by launching the compositor natively positioned on the hub display from the start (no post-launch move): Paint filled the full requested height exactly, every time. Since the real kiosk workstation only has the one (hub) display, `CompositorWindow` will always start there natively — this should not occur in actual deployment. No code changes were needed; this was purely a testing artifact.

This doesn't affect browser cells (WebView2) at all — Google, Google Maps, and YouTube all rendered correctly throughout.

## Critical bug found via real usage: one bad binding blacked out the whole wall (2026-09-17)
The user bound a cell to `www.google.com` (no `https://`) via the editor, clicked "Launch Wall", and their screen went black. Root cause, confirmed live from `activity.log`:

```
Unhandled exception: System.UriFormatException: Invalid URI: The format of the URI could not be determined.
   at NocDisplayHub.Compositor.CompositorWindow.StartBrowserCell(...)
```

`new Uri(value)` throws for a scheme-less string. That alone would only need to break one cell — but `BuildCells`'s `foreach` loop had no per-cell exception handling, so the exception escaped the loop entirely partway through the *first* cell, meaning **none of the 6 cells were ever built** — not even the 5 that had nothing wrong with them. The global `DispatcherUnhandledException` handler caught it and kept the app alive (as designed), but the window was left showing nothing but its bare black background — indistinguishable from a frozen/dead screen. The broken "NOC Display Wall" window was still open and had to be closed manually.

**Fixed, two layers:**
1. **Prevention** — `UrlNormalizer.NormalizeBrowserUrl` (Core, unit-tested) prepends `https://` to a bare domain, called from the editor's `ApplyToCell_Click` before saving. The common mistake (typing a domain the way you would in a browser bar) never reaches the compositor at all.
2. **Isolation** — `BuildCells` now wraps each cell's `StartContent` call in its own try/catch. A failure shows a specific, readable error *on that one cell* (red border, e.g. "Invalid URL:\n<value>") via an extended `LogAndGiveUp(runtime, reason, displayText)`, and — critically — the loop continues to the next cell instead of aborting. Verified live: a deliberately malformed URL (`"not a valid url at all!!"`) in one cell showed a clear error while the other two cells (Google, YouTube) rendered completely healthy next to it.

This same isolation now protects against *any* unexpected exception during cell startup, not just malformed URLs — a defensive fix, not a narrow one.

## Editor UI redesign (2026-09-17)
`EditorWindow` was rebuilt visually using the frontend-design skill — a "hardware rack panel" identity (dark nameplate header with a pulsing status LED, bezeled grid preview with per-cell coordinate tags and status LEDs, Cascadia Mono for data/coordinates, tracked-out caps for labels) instead of a generic dark dev-tool theme. Two bugs found and fixed while building it:
- `Window Background="{StaticResource VoidBrush}"` threw `XamlParseException: Cannot find resource named 'VoidBrush'` — a `Window`'s own attributes are evaluated before its `<Window.Resources>` child element is parsed, so a `StaticResource` defined there isn't available yet. Fixed by hardcoding the Window's `Background` directly instead of referencing the resource.
- Adding the widget-split row to the assignment panel pushed the bottom controls (Apply/Unassign, the auto-launch checkbox) past the fixed window height. Fixed by growing the window and shrinking the preview canvas's fixed height. This is the same class of bug as the first time this happened when the split-panel row was added — worth remembering that any new row in this fixed-height `DockPanel` needs the window height rechecked.

Then the grid preview itself (`PreviewCanvas`) didn't rescale when the editor window was resized — it was a fixed-size `Canvas` sized in pixels, so resizing the window just clipped or left dead space around it instead of scaling the layout. Fixed by wrapping it in `<Viewbox Stretch="Uniform">` and giving the `Window` a `MinHeight`/`MinWidth` so the toolbar rows can't get squeezed into overlapping each other at small sizes. Verified live: maximizing the editor scales the grid (bezel gaps, coordinate tags, status LEDs) up proportionally and keeps it centered; restoring back down scales it back with no distortion.

## Wall auto-orient + stop control (2026-09-17)
Two operability gaps found through live use:

**"Launch Wall" always opened at (0,0), not necessarily the hub.** `CompositorWindow`'s XAML had `Left="0" Top="0"` hardcoded. On the real kiosk that's correct — the hub's display is the *only* display, so (0,0) is always right. But wherever more than one screen is actually attached to the Windows session (the dev machine, or the hub temporarily sharing a workstation with a normal monitor), (0,0) is just whichever screen happens to be primary, which is not necessarily the hub. Fixed with `HubDisplayLocator.FindHubOrigin()` — enumerates Windows' GDI screens via `EnumDisplayMonitors`/`GetMonitorInfo` and looks for the *one* screen whose resolution exactly matches `HubSpec` (1920×1080), positioning the compositor there. This is a different thing from the multi-monitor rule elsewhere in this file: it does not treat the hub's 6 physical monitors as 6 OS monitors — it's a one-time "which single screen do I cover" lookup before positioning the one compositor window, run once at construction.

**First version of the fix had a real bug, caught by testing on the actual dev hardware:** the dev laptop's own built-in panel is *also* physically 1920×1080 (Windows reports it as 1536×864 only because of 125% DPI scaling) — an exact tie with the hub's resolution. `FindHubOrigin` originally treated any non-unique match as unresolvable and fell back to (0,0), which is always the primary monitor, which on this machine is the laptop's own screen — so the wall launched covering the dev display instead of the attached hub (reported by Windows as "MACROSILICON", the capture-chip name), exactly backwards from the fix's intent. Fixed by adding a tiebreak: when multiple screens match the resolution, prefer whichever ones are *not* the OS-designated primary monitor. Nobody sets the hub-fed output as their Windows primary display, so this holds in every realistic setup, and it's moot on the real kiosk where there's only one screen to match at all. Verified live after the fix: the wall opens exclusively on MACROSILICON, the built-in display stays untouched, and toggling the wall off and back on repeats correctly.

**No way to end the wall except Alt+F4 or Task Manager.** `WindowStyle="None"` means there's no title bar or close button. First attempt added a small always-on-top "STOP WALL" overlay window layered on top of the wall itself — but per the user's stated preference that interaction belongs on the editing UI, not the kiosk display, this was moved: the editor's own "LAUNCH WALL ▶" button now doubles as the stop control. `EditorWindow` holds a reference to the `CompositorWindow` it launched; while it's running the button relabels to "■ STOP WALL" (`DangerButton` style, red) and closes that window on click; the `CompositorWindow.Closed` event resets the button back to "LAUNCH WALL ▶" regardless of how the wall actually closed (this button, or an Alt+F4/crash on the wall side). Verified live: launching and stopping the wall from the editor toggles the button correctly each time, and the wall only ever appears on the hub display, never on the editor's own screen.

## Native app picker instead of a typed path (2026-09-17)
Requested: selecting "Native app" as the SOURCE type should open a file picker to choose the executable, rather than expecting a hand-typed path. `SourceTypeCombo_SelectionChanged` now toggles `ValueTextBox.IsReadOnly` based on the selected type, and a `PreviewMouseLeftButtonDown` handler on the textbox opens a `Microsoft.Win32.OpenFileDialog` (filtered to `*.exe`) whenever the type is Native app, writing the chosen path into the field. Browser URL keeps the field free-typed, since typing a URL directly is the normal way to enter one.

**Caught a real startup-crash bug while first testing this live:** the app launched, the process stayed alive, but no window ever appeared — `Get-Process` showed `MainWindowHandle = 0` indefinitely. `activity.log` had the actual cause: `SourceTypeCombo_SelectionChanged` NullReferenceException'd on `ValueTextBox`, because the XAML marks the "Browser URL" `ComboBoxItem` as `IsSelected="True"`, which fires `SelectionChanged` *during* `InitializeComponent()` itself — before `ValueTextBox` (declared later in the visual tree) has been assigned by the generated field-init code yet. The global `DispatcherUnhandledException` handler caught it and kept the process running (as designed, see the black-screen-wall entry above), but since the exception happened inside the `EditorWindow` constructor, `Show()` was never reached, so the app just sat there with no window and no crash dialog — easy to mistake for a hang. Fixed with a null guard at the top of the handler. Worth remembering for any future `SelectionChanged`/similar handler wired to a XAML element with a default selection: it can fire before sibling named elements are initialized.

## Native app target: folders, documents, and images too (2026-09-17)
The native-app picker only let you choose an `.exe`, which couldn't express two things a real NOC dashboard needs: opening File Explorer on a *specific* folder (e.g. a shared logs or drop folder — `explorer.exe` alone just opens wherever the shell's default view is, not a chosen folder), and pointing a cell straight at a document or image (opened via whatever app Windows has associated with it).

**Folder targets:** added a second "OR PICK A FOLDER…" button next to the Value field (visible only for Native app), using `Microsoft.Win32.OpenFolderDialog`. A folder path with no `.exe` at all is a valid binding — `NativeAppHost.IsShellHostedTarget` (renamed from `IsExplorer`) now also matches `Directory.Exists(exePath)`, routing it through the same shell-window-tracking path already built for `explorer.exe` (see the entry above), since `ShellExecute`-opening a bare directory hands off to the running shell exactly the same way.

**Document/image targets:** broadened the app picker's filter beyond `*.exe` to include common document (`pdf`/`doc`/`docx`/`xls`/`xlsx`/`ppt`/`pptx`/`txt`) and image (`jpg`/`jpeg`/`png`/`gif`/`bmp`) extensions, plus "All files". These launch through the existing generic `AttachAsync` path unchanged — `ProcessStartInfo(..., UseShellExecute = true)` already opens any file type via its default handler. Caveat worth remembering: if the default handler for a given file type is a modern single-instance/MSIX app (the same category as Notepad and Photos), it'll hit the same "redirection stub" behavior already documented above — timeout, retry, then a clean give-up message on the cell, not a crash, but also not a live view of that file. Classic multi-instance viewers work as expected.

## Editor window overflow on smaller screens (2026-09-17)
The editor's default `960x940` size is comfortable on a full-size monitor, but on a smaller display (or the same display at higher DPI scaling) it could be taller than the actual usable desktop area, pushing the bottom controls (Apply/Unassign, the auto-launch checkbox) past the visible screen edge — confirmed live: the window opened with its bottom row of controls off-screen. Fixed in the constructor, before the window is ever shown: `Height`/`Width` are clamped to `SystemParameters.WorkArea` (which excludes the taskbar), never below the existing `MinHeight`/`MinWidth`. `WindowStartupLocation="CenterScreen"` was also added so a shrunk window doesn't end up off-center. The grid preview already scales to fit via its `Viewbox` (see the resize-fix entry above), so a smaller window just means a smaller preview, not clipped controls. Verified live: window now opens fully on-screen with every control visible, confirmed by comparing its actual `GetWindowRect` against the screen's real work area.

## Generalized the "launcher hands off and exits" fallback beyond Explorer (2026-09-17)
Bound a cell to Viber (a real chat app, not a test stand-in) and it never showed — `activity.log` showed the exact same `Process exited before a main window appeared` / "likely handed off to an already-running instance" failure already documented for `explorer.exe`, confirmed live even on a genuinely cold launch (Viber's process fully killed first, then relaunched) — so this isn't just the "already running" case; Viber's own launcher exits after handing off to a real worker process even on a first start. This is presumably common among Electron/Qt-style chat and collaboration apps generally, not a one-off Viber quirk.

Generalized `NativeAppHost`'s existing Explorer-only fallback (`AttachShellWindowAsync`, keyed off Explorer's known, stable `CabinetWClass` window class) into something that works for apps without a documented window class: when the launched process exits without ever owning a window, `AttachAsync` now falls back to watching for a *new* top-level, titled, visible window owned by *any* currently-running process sharing the launched exe's image name (`FindTopLevelWindowsByProcessName`/`WaitForWindowByProcessNameAsync`), within the same timeout budget. Found this way, the window is tracked by handle only (`AttachResult.Process = null`), never by the process we launched — same non-kill safety rule as Explorer's window, since we don't actually own whatever process ends up owning it.

**Verified directly:** wrote a temporary diagnostic entry point (`--diag-native-app <path>`, removed after use) to call `NativeAppHost.AttachAsync` in isolation and log the result, since the interactive UI test kept getting disrupted by this dev machine's aggressive focus-stealing (Razer Synapse, Viber's own notifications — see below). Confirmed Viber's cold-launched window is found and reparented successfully. **Not fully verified:** the specific "different process, same image name" fallback branch itself, since Viber turned out to have its own separate wrinkle — **it starts minimized to the system tray with an invisible main window once already logged in** (confirmed via full window enumeration: a real `Chrome_WidgetWin_0` window exists but `IsWindowVisible` is false), which no reparenting approach can show, since there's genuinely no visible content at that point. If Viber (or a similar always-on chat app) needs to show live in a cell, check its own settings for a "start minimized to tray" option and disable it — that's a Viber-side fix, not something `NativeAppHost` should try to override, since plenty of apps intentionally start hidden on purpose.

**Unrelated finding from the same testing session, worth remembering:** this dev machine has apps (Razer Synapse, Viber) that repeatedly steal OS foreground focus unprompted. Several "the click didn't work" moments during this session turned out to be exactly that — not an app bug. If a click-driven test seems to silently fail with no error and no exception logged, re-confirm which window actually has focus before assuming the app is broken.

## Single-instance guard + cross-process log-write hardening (2026-09-17)
Confirmed live: nothing stopped a second copy of the app from running — double-clicking the exe directly (instead of using the editor's "Launch Wall") spins up a fully independent second process, which reads/writes the same `profile.json` and `activity.log` as the first. A real symptom of this was caught during testing: with an editor and a standalone wall both running, a cell's native-app failure produced *no* log entry at all instead of the expected "Failed to launch"/"Giving up" pair, and the cell never even reached its red error state — silently stuck instead of failing visibly.

Root cause: `ActivityLog.Write`'s `lock` only serializes threads *within* one process; a second process opening the same file for append at the same instant throws `IOException`, and since `LogAndGiveUp` calls the log write *before* updating the cell's UI, that exception aborted the give-up logic entirely, before ever reaching the visible "Dark" state. Fixed with a short retry-with-backoff (5 attempts, 40ms apart) around the actual file write — enough to ride out a momentary cross-process collision without letting it break error handling that's specifically supposed to never fail.

Fixed the actual cause too, not just its symptom: `App.OnStartup` now claims a named, machine-wide `Mutex` (`Global\NocDisplayHub_SingleInstance`) before doing anything else. A second launch attempt (editor or wall, either way — the mutex doesn't distinguish) finds the mutex already held, activates the existing instance's window (`SetForegroundWindow`) instead of doing nothing silently, and exits immediately without ever creating a window of its own. Verified live: launching the exe a second time while an editor was already open brought the existing editor window to the foreground and created no second process.

## Predicted native-app compatibility (2026-09-17)
Based on everything found reparenting real apps so far (Notepad, Paint, Character Map, File Explorer, Viber) — a prediction to check candidates against before binding them, not a tested guarantee. **Browser cells have none of these problems**; this section is native-app (`SourceTypeCombo` = "Native app") only.

- **Likely fine:** classic Win32 desktop apps that open a genuinely new top-level window on every launch — Paint (classic), Character Map, most legacy utilities, most classic multi-instance PDF/image viewers (e.g. PDF-XChange, IrfanView, if installed and set as the default handler).
- **Broken by design — Microsoft Store / MSIX redirection stub:** the launched process never becomes the real window owner and just times out (already documented above for Notepad; the same applies to the Store versions of Paint, Calculator, and the built-in **Photos** app — the default handler for images on a stock Windows install). If a bound image/document opens in one of these, expect a timeout-then-give-up, not a crash, but also not a live view.
- **Broken by design — starts hidden/minimized to tray:** confirmed with Viber once already logged in. No reparenting approach can show a window that isn't rendering. Check the app's own settings for a "start minimized" option.
- **Works only on a genuinely cold start, not if already running:** anything with a singleton/launcher-hands-off pattern (Explorer, Viber, and presumably similar Electron/Qt-shaped chat and collaboration apps generally — Slack, Discord, Telegram, WhatsApp Desktop are reasonable guesses, untested). If the app is already open somewhere else when the wall starts, launching it again just reactivates that existing window rather than creating a new one — and the fallback built for this only recognizes *new* windows, deliberately, to avoid one cell grabbing a window that belongs to something else. **Outlook is a special case of this worth flagging early:** it's normally already running in the background on any real office workstation checking mail, and only ever has one real instance per profile — a very likely candidate to hit exactly this limitation.
- **MS Office (Word/Excel/PowerPoint/Outlook) — confirmed and fixed 2026-09-17:** the splash-window risk predicted above was real. See "Window-swap recovery" below.

None of this is a reason to avoid a given app outright — browser-based dashboards sidestep all of it, and even the "broken by design" native-app cases fail safely (a clear give-up message, never a crash or a black wall) per the isolation work above. It's a reason to test a specific candidate app early, before committing a whole cell's layout to it.

## Window-swap recovery + honest reparent status (2026-09-17)
Bound a cell to Outlook and confirmed the predicted splash-window risk directly: Outlook launched fine and the cell showed a green "Healthy" border, but the cell was actually black. Investigation found the window Outlook was *currently* showing had never been touched by our code at all (`GetParent() = 0`, and its style bits still had `WS_CAPTION` — `Reparent` strips that, so this window was never reparented). Outlook's launcher window (an early splash/loading frame) had already been destroyed and replaced by a completely new top-level window once Outlook finished loading — exactly the "MS Office splash-then-real-window swap" risk flagged in the compatibility list above, now confirmed live.

Two compounding bugs made this worse than a simple missed edge case:
1. **`SetParent`'s return value was never checked.** `NativeAppHost.Reparent` called it and moved on regardless of success — so a cell could report "Healthy" even if the OS-level reparent silently failed. Fixed: `Reparent` now returns `bool` (checking `GetLastWin32Error` too, since `SetParent` returning NULL is ambiguous — it also means "had no previous parent," the normal case for an ordinary top-level window), and every call site throws on failure instead of reporting false success.
2. **The watchdog only checked `Process.HasExited`, never the window itself.** A process that swaps to a new window without ever exiting looked identical to one running perfectly fine. Fixed: `CellRuntime.TrackedWindowHandle` is now set for *every* successful native-app attach (not just shell-hosted ones like Explorer — `Process` may be set alongside it now), and `RunWatchdogPass` checks `NativeAppHost.IsWindowAlive` on it directly, every tick, for every native-app cell. When the tracked window is gone but the owned process is still alive, the watchdog now calls `process.Refresh()` and re-reads `MainWindowHandle` — if it's a genuinely new window, it gets reparented automatically, recovering silently to Healthy. If the process is alive but has no usable window yet, the cell shows "Restarting" and gets a few more ticks (reusing the existing `ConsecutiveFailures` cap) before giving up, rather than either relaunching the whole app unnecessarily or waiting forever.

**Verified live end-to-end:** launched Outlook, watched the watchdog's very next tick log `Reparented a new window from the same still-running process...` and immediately show live Inbox content — folder pane, message list, ribbon, all correctly clipped inside the green-bordered cell.

## Drag-and-drop window capture (2026-09-17)
Real problem this solves: opening an email or meeting item in Outlook (or any secondary window a native app spawns after being embedded) creates a brand-new top-level window our reparenting never knows about — it just floats independently. Since the hub is one shared desktop with one cursor spanning every physical monitor, dragging that stray window directly onto a cell is a natural gesture here in a way it wouldn't be on a normal multi-monitor desk. Explicit direction from the user: capture *any* window dropped onto a cell, no "capture mode" toggle first — a wrong drop is trivially corrected by dragging the right window on top of it afterward.

`WindowDragWatcher` installs a `SetWinEventHook` for `EVENT_SYSTEM_MOVESIZEEND` (with `WINEVENT_SKIPOWNPROCESS`, so our own windows are automatically excluded — a reparented window has no caption left to drag by anyway, per `Reparent` stripping `WS_CAPTION`) — this is the purpose-built Windows API for "tell me when any window, including ones I don't own, finishes being dragged," and needs no DLL injection. `CompositorWindow.OnWindowDropped` checks the dropped window's final screen position (`NativeAppHost.TryGetWindowRect`) against every cell's bounds; a hit calls `CaptureDroppedWindow`, which:
- Gives back whatever the cell was showing before as an ordinary independent window (`NativeAppHost.Release`, the exact inverse of `Reparent` — restores the caption/frame/system-menu style bits and detaches the parent) rather than silently orphaning it. Its process is never touched, only the window.
- Reparents the newly-dropped window in, tracked purely by handle (`Process` left null — we don't own whatever app this actually is).
- None of this touches `profile.json`. A drag-drop capture is deliberately runtime-only, the same way Explorer's window was already never "reconstructed" from the profile — if the wall restarts, the cell goes back to whatever's actually persisted for it.

**Verified live end-to-end, both directions:** dragged Character Map onto an empty cell — captured, resized, rendered correctly, logged. Then dragged Notepad on top of that same now-occupied cell — Notepad took over the cell, and Character Map was confirmed released back to being a normal floating window at its old position (`GetParent() = 0`, still visible, not lost or closed), exactly the "wrong drop is trivially correctable" behavior requested.

**Follow-up fixes the same day, both from real usage on the actual hardware:**
- **Displaced windows now minimize instead of floating in place.** `Release` left the old window sitting at the cell's screen coordinates, which on the real single-display kiosk don't correspond to the workstation's own screen — it would just crowd whatever screen it actually resolved to. `Release` now calls `ShowWindow(SW_MINIMIZE)` right after detaching.
- **Minimizing alone wasn't enough — confirmed live, restoring it popped it right back over the wall.** Windows remembers wherever a window was positioned immediately before minimizing as its "restore" position, which was still the cell's coordinates on the hub display — so un-minimizing it later (clicking it in the taskbar, Alt+Tab, etc.) put it right back on top of the wall. Fixed by having `Release` move the window onto the primary monitor (always anchored at `(0,0)` by Windows convention, size read via `GetSystemMetrics(SM_CXSCREEN/SM_CYSCREEN)`) immediately before minimizing, so that becomes its remembered restore position instead. **Not yet re-verified live** — this dev machine was in active use elsewhere on every attempt today; needs confirming on the real wall.
- **A dragged-in browser window left a black gap around its content — fixed, confirmed live.** A URL/browser window captured via drag-and-drop rendered with visible black space around it after being resized into its cell — unlike Character Map's "not designed to resize at all" limitation (see the compatibility list above), a browser is fully resizable by design, so this pointed at something more specific. Browsers (and other GPU-accelerated/DirectComposition-backed apps) don't always recompute their composited window surface from a single `SetWindowPos` call, leaving stale, undersized content — the same general category as the intermittent "wrong cell content" glitch documented above, both rooted in how DirectComposition surfaces respond to being resized programmatically rather than through normal user interaction. Fixed in `Reposition` (used by every `Reparent`) with a standard, low-risk remedy for this class of issue: resize once to 1px smaller, then immediately to the real target size — two genuinely different `SetWindowPos` calls back-to-back force a full surface recompute, imperceptible since nothing renders between them. **Confirmed on the real wall: drag-and-dropped windows now fit fine.**

## WebView2 gap on normal browser cells (2026-09-17)
Photo from the real wall showed the *opposite* case of the fix above: several normal browser cells (bound the regular way, via SOURCE/VALUE — not drag-and-dropped) each had a visible black gap between the green status border and the actual page content. Confirmed via live user feedback that drag-and-dropped windows fit fine, narrowing this specifically to `StartBrowserCell`'s WebView2 path, which never touches `InsetForBorder`, `Reparent`, or anything else changed above — a separate bug in the same general family, not a regression from those fixes.

Root cause: WebView2 hosts its own Chromium composition surface via a native child HWND under the hood, and on this compositor's borderless window — explicitly positioned on a non-primary monitor via `HubDisplayLocator`, with a `PerMonitorV2` manifest — that surface can end up sized against a stale/incorrect DPI or bounds assumption from before the window settled into its final monitor context, never self-correcting afterward. This is a known class of WebView2 sizing issue in exactly this kind of non-default window setup.

Fixed with the WPF-level equivalent of the `Reposition` double-resize trick, since WebView2 in WPF is a managed `FrameworkElement`, not something manipulated via raw `SetWindowPos`: `NudgeWebViewLayout` (called once `CoreWebView2InitializationCompleted` succeeds) sets `Width`/`Height` to the control's current size minus 1px, calls `UpdateLayout()`, then clears both back to `NaN` (restoring normal Stretch layout) and calls `UpdateLayout()` again — two genuinely different layout passes back-to-back force WebView2's `HwndHost` to re-arrange its native surface against the correct bounds. **Reported still present after this fix** — but the live wall session the user was checking against had been running continuously since before this fix was even built, and `StartBrowserCell` only runs once per cell at launch; a code fix here can't retroactively apply to an already-running WebView2 instance. Needs re-testing after a full wall restart before concluding the nudge itself is insufficient.

## WebView2 DPI/zoom scaling — content rendered "cut from a bigger pie" (2026-09-17), fix reverted same day
Live user report, describing page content in browser cells as looking zoomed-in and cropped — like viewing a slice of a larger rendering — while everything within that crop stayed internally proportional. Diagnosed at the time as WebView2 rendering against the wrong device-scale factor, and "fixed" by setting `webView.ZoomFactor = 1.0 / VisualTreeHelper.GetDpi(this).DpiScaleX` once `CoreWebView2InitializationCompleted` succeeded (`CoreWebView2Controller.RasterizationScale`, the architecturally-correct lever, isn't exposed on the public WPF `WebView2` control at all — confirmed via the package's own API docs, it's `internal`-only).

**Reverted the same day, based on direct user feedback: "it was working well until I asked for scale fixing."** Wrong theory, wrong fix. `ZoomFactor` is Chromium's actual page-zoom feature (the same thing as Ctrl+/Ctrl- in a normal browser) — it doesn't correct a rasterization/DPI mismatch, it changes how many CSS pixels fit in the viewport, which can reflow a responsive site's entire layout rather than just resizing it. That's very likely what made things look *worse*, not better.

The more useful frame going forward, from the user's own words: **"each cell become the 100% of vh and vw... it's literally like another device/external monitor."** This is exactly right, and it isn't a bug — a `WebView2` control, like any embedded browser, always treats its own allocated pixel area as 100% of the viewport. It has no concept of "the rest of the desktop." If a given website's own responsive design doesn't look right at a specific cell's pixel dimensions, that's a property of that site, not something this compositor can universally correct — there is no single fix that makes every website look right at every possible cell size. `NudgeWebViewLayout` (the black-gap fix, a separate and still-valid concern) is untouched by this revert.

## ZoomFactor brought back the same day, used correctly this time: fake a full-size viewport on purpose (2026-09-17)
Live screenshots showed the practical consequence of the "each cell is its own monitor" fact above: a fixed-width login card (and Google's own homepage) reflowing badly — visible scrollbars, cut-off field labels (`ername`/`ssword` instead of `Username`/`Password`, the page rendered wider than the visible area and scrolled partway across) — once squeezed into anything smaller than a full 1×1 cell. ## Chrome-closing-on-shutdown bug, minimize-restore fix, and drag-and-drop watchdog gap (2026-09-17)
Three fixes from the same live-testing pass:

**Critical: closing the wall closed the user's entire Chrome browser, including tabs never touched by the wall.** The user had several Chrome tabs open, dragged specific ones onto cells (drag-and-drop capture), left others alone on the main monitor — and closing the wall closed the whole browser, all tabs included. Root cause: `OnClosed` sent `WM_CLOSE` uniformly to every cell's tracked window, including ones only borrowed via drag-and-drop capture, never actually owned. Chrome-family multi-window apps decide whether to fully quit based on how many top-level windows they still have; reparenting silently drops a window from that count without the browser knowing, so it can conclude its last real window just closed even when others are still open elsewhere. Fixed with a new `CellRuntime.IsDragDropCaptured` flag, set true by `CaptureDroppedWindow` and false by a normal `StartNativeAppCellAsync` launch. `OnClosed` now branches on it: `NativeAppHost.Release` (give the window back, never touching its process) for anything drag-and-drop-captured, `NativeAppHost.CloseWindow` (unchanged) for anything the wall actually launched itself (a normal native-app binding, or Explorer). **Verified live on the dev machine 2026-09-17** using a real `SendInput`-driven mouse drag (not a synthetic reparent call — an actual interactive drag, confirmed to trigger `WindowDragWatcher`'s `EVENT_SYSTEM_MOVESIZEEND` hook exactly like a real user gesture would) of Character Map onto a wall cell, then clicking "Stop Wall": Character Map's process stayed alive and responding throughout, with its original window handle restored as a real top-level window again — proving `Release` (not `CloseWindow`) was the path taken. Chrome itself isn't installed on this dev machine to test the exact multi-tab scenario, but the mechanism this bug lived in (`OnClosed`'s per-cell branch) is exactly what was exercised here, for any drag-and-drop-captured window regardless of which app it belongs to.

**Minimize-then-restore still opened back over the wall — first attempted fix didn't hold.** The follow-up fix from the drag-and-drop section above (`Release` moves the window to the primary monitor, then minimizes) was reported as not working: restoring a minimized displaced window still popped it back over the wall. Root cause: `SetWindowPos` (move) and `ShowWindow(SW_MINIMIZE)` are two separate, non-atomic Win32 calls — nothing guarantees the position change actually committed to the window's tracked "restore" rect before the very next call minimizes it, especially back-to-back with no message-loop turnaround in between. Rewrote `NativeAppHost.Release` to use `GetWindowPlacement`/`SetWindowPlacement` instead — the documented, atomic way to set both a window's show state and its remembered restore rect (`rcNormalPosition`) in one call, closing the ordering gap entirely. **Verified live on the dev machine 2026-09-17**, same test as above: after `Release`, `GetWindowPlacement` showed `showCmd = SW_SHOWMINIMIZED` with `rcNormalPosition` anchored at (100,100) — well inside the primary monitor, nowhere near the hub display's `x ≥ 1920` region — and manually restoring it (`ShowWindow(SW_RESTORE)`) landed it exactly there, confirmed via `GetWindowRect`, never back over the wall.

**Found during this review, not from a live report: the watchdog silently never checked drag-and-drop-captured cells whose original persisted binding wasn't already NativeApp.** `RunWatchdogPass`'s very first line skipped any cell where `Cell.Binding?.Type != BindingType.NativeApp`, with no exception for a cell that had since been overwritten by a drag-and-drop capture (the common case — most captures land on a cell that was Unassigned or Browser-bound, not NativeApp-bound). That meant a dragged-in window dying — closed manually, or the app crashing — went completely undetected: the cell just sat there showing dead space forever, no red border, no relaunch, no log entry. Fixed by adding `&& !runtime.IsDragDropCaptured` to the skip condition, and by having the fallback-relaunch path capture whether the cell *was* drag-and-drop-captured before clearing the flag, then dispatching through `StartContent` (the same Browser/NativeApp/Unassigned switch `BuildCells` uses) instead of unconditionally calling `StartNativeAppCellAsync` — which would have thrown a `NullReferenceException` on `Cell.Binding!.Value` for a cell whose real persisted binding is Unassigned, or nonsensically tried to launch a URL as an executable path for one that's Browser-bound. There's no way to "relaunch" an arbitrary window someone dragged in — it isn't a path or URL the app owns — so falling back to the cell's actual configured binding (possibly nothing at all) is the only sane recovery. Also fixed a related smaller gap in `CaptureDroppedWindow`'s rare defensive branch (the dropped window somehow already claimed by a different cell): it wasn't resetting that other cell's `IsDragDropCaptured` back to `false`, which would have left it permanently mis-flagged (any future close of *that* cell would try to `Release` a window it no longer has, instead of doing nothing).

## Browser navigation failures and activity-log write exhaustion (2026-09-17)
Two gaps found during the same review pass, neither yet reported live but both clearly reachable in normal operation:

**A browser cell whose navigation failed had no recovery path at all.** `StartBrowserCell`'s `NavigationCompleted` handler only had a success branch — a failed navigation (no network yet at kiosk boot, DNS not resolved, a host that's briefly unreachable) left the border on whatever it already was (typically the initial orange "Restarting" placeholder) forever, with no log entry, no red-border error state, and no retry — `RunWatchdogPass` deliberately skips Browser cells entirely, so the *only* thing that would ever touch it again was `RunScheduledRefreshPass`, up to 30 minutes later (`RefreshSettings.Interval`). This is a real risk specifically for the kiosk's auto-launch-on-boot path (see "App auto-launches on Windows startup" above) — if the network isn't up yet when the wall starts, every browser cell could get stuck looking like it's perpetually "still starting" for half an hour. Fixed: a failed navigation now logs the `WebErrorStatus`, increments `ConsecutiveFailures` (giving up past `MaxConsecutiveFailures`, same cap as everything else), and retries via `RetryNavigationAsync` on a short backoff (2s × failure count, capped at 10s) rather than waiting for the scheduled refresh.

**`ActivityLog.Write` could still throw after exhausting its cross-process-lock retries, undermining its own purpose.** The retry loop (added earlier to survive a second process instance briefly holding the log file) let the final attempt's `IOException` propagate uncaught once `MaxAttempts` was reached. Since `ActivityLog.Write` is called from inside cell error-handling paths like `LogAndGiveUp` *before* the UI update that shows the cell's red border/error text, an exhausted-retry exception there would abort `LogAndGiveUp` mid-way — silently leaving the cell showing nothing, exactly the failure mode the retry logic exists to prevent, just deferred to a lower-probability (but still real) case of an unusually long-held lock. Fixed by swallowing the final attempt's `IOException` too — logging is now genuinely best-effort, and a lost log line can never take down the caller's own error-recovery UI update.

Both fixed, build clean, 33/33 tests pass. Neither yet re-verified live.

## Drag-and-drop-captured browser windows keep their own tab strip and window buttons, sometimes cropped — unresolved, not a bug in our reparenting code (2026-09-17)
Live report (screenshot from an earlier session): a browser window captured via drag-and-drop showed its own tabs and title-bar-style minimize/close buttons inside the cell, sometimes visually cropped/cramped against the cell's edges. Asked at the time ("what are the tabs for that cell even the other button for exit or minimize") but never actually fixed — flagged again later as still outstanding.

Root cause: `NativeAppHost.Reparent` only strips the OS-level non-client chrome (`WS_CAPTION`/`WS_THICKFRAME`/`WS_SYSMENU`) — the classic Windows-drawn title bar. But every Chromium-based browser (Chrome, Edge) draws its own tab strip and window-control buttons itself, inside the client area, not via the OS non-client frame. Stripping `WS_CAPTION` does nothing to that self-drawn UI — it was never OS chrome to begin with. So a captured browser window keeps rendering its own tabs/buttons exactly as it always does; squeezing that whole window down into a cell just cramps or clips those elements against the cell's bounds instead of removing them.

**Not fixable at the reparenting layer** — there's no Win32-level way to suppress a browser's self-drawn UI from outside the process; the only way to get a chrome-free view of that browser's content would require cooperation from the browser itself (e.g. relaunching it with `--app=<url>` kiosk-style flags), which doesn't apply to a window someone already had open and is dragging in after the fact — the entire point of drag-and-drop capture is grabbing arbitrary already-running windows as-is.

**Practical guidance:** drag-and-drop capture is for ad-hoc secondary windows (an opened email, a popped-out document, a Character-Map-style utility) — not a substitute for a proper cell binding. Anything meant to be a permanent, clean dashboard view of a website should use a **Browser/URL binding** (WebView2) instead, which renders only the page with zero browser chrome. This is a design limitation of drag-and-drop capture, not a defect to keep chasing.

## ZoomFactor's width-only calculation left an empty gap at the bottom of every cell (2026-09-21)
Live report with a screenshot of real DENR/EMB air quality Power BI dashboards on the wall: every 2x3 cell had a large empty (black) gap below the actual report content — roughly a third of the cell's height. Called "white space" by the user but same underlying mechanism regardless of color.

Root cause: `webView.ZoomFactor = cellWidth / HubSpec.InputWidth` (the "fake a full-size viewport" fix from earlier the same week) only matches the WIDTH dimension of the pretend full-size viewport. `ZoomFactor` is one uniform scalar applied to both axes, so it can only make ONE dimension of the effective viewport (`physical size / zoom`) match `HubSpec` exactly. A 2x3 grid cell's aspect ratio (~1.19:1) is narrower than `HubSpec`'s 16:9 (~1.78:1), so width-only zoom left the effective viewport HEIGHT taller than a real 1920×1080 screen would give (a 640×540 cell computed an effective ~1920×1620) — dashboards designed for a normal screen don't stretch to fill that extra height, so the surplus showed as blank space at the bottom.

Fixed by using `Math.Max(cellWidth / HubSpec.InputWidth, cellHeight / HubSpec.InputHeight)` instead of width alone — this makes the effective viewport's SMALLER dimension match `HubSpec` exactly (eliminating the gap on that axis), at the cost of the other dimension coming in narrower than a full-size screen would be (i.e. very slight cropping instead of empty space). A full 1×1 cell is unaffected either way (both ratios are already 1.0 there).

**Verified live:** before/after screenshots of the same real dashboard wall. The empty gap is gone — Power BI's own report chrome (zoom-level indicator, page navigation arrows, "Microsoft Power BI" branding) that was previously pushed down into the empty space is now visible again, meaning the effective viewport height now actually matches what the reports were designed for.

## Major open question, unresolved: dev-machine screenshots may not reflect what the real wall shows, because of a stretch the hub applies that only exists on real hardware (2026-09-21)
Chased a follow-up to the white-space fix above: tried oversizing `WebView2` to a true 16:9 shape and clipping the overflow, so the effective viewport Power BI sees would have exactly `HubSpec`'s aspect ratio instead of the cell's own (~1.19:1 for a 2x3 cell). It worked — the Airsheds blank space disappeared entirely — but it cropped real content (filter panels, titles) off the left edge of every cell. Flagged this trade-off to the user before committing either version.

**While discussing it, a bigger question surfaced that puts every dev-machine screenshot in this file under question.** Confirmed with the user: each physical TV in the 6-monitor wall (a) is a standard 16:9 panel, and (b) stretches whatever cropped portion of the signal it receives to fill its own full screen. For the current 2x3 profile, that crop is 640×540 (~1.19:1) — stretching that non-uniformly to fill a 16:9 screen means **3.0x horizontal vs. 2.0x vertical**. That's a real, mathematically-necessary distortion on the physical hardware that **cannot be reproduced or previewed from this dev machine**, which only has one plain, unstretched test monitor standing in for the hub.

This means the two zoom experiments need to be re-evaluated backwards from how they looked here:
- The **currently-shipped fix** (`Math.Max` of width/height ratios, locking the effective viewport to the cell's own squished aspect ratio) looked like it had *more* blank space in dev screenshots — but if the TV's own non-uniform stretch un-squishes that same content back toward correct proportions, this could actually be the *more* correct choice on the real wall, not less.
- The **reverted 16:9-clipping experiment** looked cleaner in dev screenshots (no blank space) — but that clean 16:9 rendering would then get re-distorted by the TV's own stretch on the real hardware, potentially undoing the fix entirely.

**Left as an open question — reverted the 16:9-clipping experiment back to the shipped `Math.Max` version rather than guess.** Neither version has been confirmed against the actual physical TVs; only the earlier dev-screenshot comparisons have been done. Next step, when the user is at the real hardware: look at *general* content (not just Power BI) for any visible horizontal stretching or distortion — something with a known real-world shape, like the Philippines map already used in several of these dashboards, is a good visual reference (does Luzon/Mindanao look elongated compared to a real map?). If there's visible distortion generally, that's a much bigger, separate problem from the Power BI white-space issue this session was chasing, and would need addressing at the `HubSpec`/cell-bounds level, not per-cell zoom tuning.
